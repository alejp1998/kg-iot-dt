📖 Digital Twin Knowledge Graph Guide
💡 What is this Project?

This system implements an autonomous Knowledge Graph Agent for Industrial IoT platforms. Instead of requiring human engineers to manually update databases when factory equipment changes, the agent listens to real-time MQTT message streams, reads SDF (Semantic Definition Format) schemas, and dynamically creates, updates, and reasons over a virtual TypeDB Knowledge Graph model in real time.

🏭 1. Factory Floor Digital Twin

Represents an automated automobile manufacturing plant divided into sequential production stations (Underpan Config → Body Config → Vehicle Scanning → Window Milling → Quality Check & Repair) linked by conveyor belts, plus indoor and outdoor environmental safety monitoring zones. Each node displays live telemetry feeds (joint positions, temperature, PM2.5/PM10 particulate matter, alarms).

🕸️ 2. TypeDB Knowledge Graph & TypeQL

Displays the complete semantic ontology (40+ concept nodes). Entities such as department, task, device, and module are bound through relations like execution, sequence, and needs. The interactive console on the right shows the exact declarative TypeQL queries compiled online.

🧬 3. Dual-Metric Semantic Discovery Engine

When an unanticipated or unknown device appears on the network, the agent automatically integrates it using a dual-similarity pipeline:

  • Syntactic/Semantic Distance: Levenshtein ratio (thefuzz) comparing Thing, Object, and Property descriptions in the device's SDF schema.
  • Behavioral Distance: Matrix profile time-series wave matching (stumpy.mass) over buffered sensor readings to find matching physical behaviors.

Case 1 demonstrates an unknown AirQualitySimplified replacing a decommissioned sensor (94.2% match), while Case 2 demonstrates a complementary PickUpRobot-2 seamlessly adopted into the chassis assembly task (98.8% match).

⏱️ 4. Agent Lifecycle & Performance

Tracks the agent's internal finite state machine: State 0: IDLE (waiting for messages), State 1: PROCESSING (parsing JSON & running similarity algorithms), and State 2: QUERYING (executing TypeQL transactions). Telemetry messages are processed with an average end-to-end latency of just ~18.4 milliseconds.
